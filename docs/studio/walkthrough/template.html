Context Studio: keep the business's definitions right, and get the same governed answer every time

A curator agent reads the company's documents and data, finds what changed, proves it, and asks the right owner to approve. Business owners review in plain language; every change is versioned and reversible. AI agents then answer through the approved ontology and governed metrics, so the same question gets the same number.

1How the curator works

The curator reads every document once, links what it finds to the ontology, checks it against the data, and decides: draft a change, ask an owner, or set it aside with a reason. Here it finds one sentence on page 3 of a regulatory bulletin among 12 documents.

  1. Reads the documents12 documents: bulletins, manuals, a treaty, a bordereau spec, plus decoys such as news and an underwriting rule.
  2. Finds the needle"Insurers shall code PFAS claims under a separate cause-of-loss code" on page 3 of a state bulletin.
  3. Proves it in the data5 claims in one unit already carry the code PFAS that the ontology does not recognise.
  4. Drafts and checksThe change is drafted and every check runs: the ontology builds, metrics resolve, SQL compiles on all platforms, totals reconcile.
  5. Routes to the ownerA regulator's rule applies industry-wide, so it goes to the industry pack's owner, who can ask the curator why before approving.
  6. Goes live, with historyApproved changes go live with who approved them and the source page. Any change can be undone, through another approval.

2How a business owner uses it

Owners never see the plumbing. They see proposals in their inbox, with the source quote, the proof in the data and the impact on governed numbers, and they approve, ask for changes or answer the curator's questions. They can also suggest changes themselves.

  1. Approves a proposalA new claim status (suspended, litigation hold) from the claims manual, with every check green.
  2. Answers a questionThe curator did not guess on a treaty change (wildfire 72 hours to 168 hours, page 41). It asked; the owner answers.
  3. Suggests a changeThe steward rewrites the business definition of Claim File; it becomes a proposal, checked and routed like any other.

Why the governed answer repeats

  • The ontology resolves "Harbor Program Group" and "loss and ALAE" to one concept, one unit and one set of joins.
  • The semantic layer computes one governed definition (reported incurred loss and ALAE over earned premium) at the governed valuation date, 2026-06-30. It is never re-derived in SQL.
  • Definitions are pinned to the approved content version. Change a definition and the answer changes for everyone, through an approved proposal.

Why the raw answers drift

  • The program administrator sends a cumulative monthly bordereau. Summing it across months counts the same claims many times.
  • Each run picks its own premium (written versus earned), joins and date logic.
  • Nothing tells it which definition the business signed off.
SELECT SUM(PAID_TD), SUM(EXP_PAID_TD) ...
FROM hpg.BDX_CLAIMS            -- cumulative snapshots, summed
WHERE BDX_MONTH <= '2026-06-30'

4What sits underneath

Every client's ontology is built in four layers. Each layer only adds or narrows, never renames, so everything built on a lower layer keeps working.

KernelWhat every insurance line shares: party, product, coverage, claim, decision.
Industry packCommercial P&C, health (commercial and Medicare Advantage), life and annuity, each with its concepts and governed metrics.
Client overlayThe company's own words and rules, as a short reviewable list of differences.
UnitsEach operating unit maps its own source system onto the shared concepts.
